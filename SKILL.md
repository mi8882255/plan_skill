# plan-tree

Инструмент для проработки архитектурных идей через дерево субагентов, с
персистентным состоянием на диске, инкрементальным пересчётом и явной
эскалацией взаимоисключающих решений пользователю.

Этот skill переносим между проектами: скопируй/симлинкни
`.claude/skills/plan-tree/` в любой другой проект. Данные конкретной идеи
(дерево плана) живут НЕ в skill, а в рабочем каталоге проекта, где skill был
вызван — по умолчанию в `./plan/<idea-slug>/`.

## Роли

- **Ты (координатор/главный агент)** — ведёшь диалог с пользователем,
  читаешь/пишешь файлы дерева, решаешь что пересчитывать, запускаешь
  субагентов, собираешь ambiguous-узлы, задаёшь пользователю вопросы через
  AskUserQuestion, записываешь вердикты. Ты НЕ прорабатываешь детали сам —
  это работа субагентов.
- **Субагент на узле** — получает сжатый контекст (см. ниже), прорабатывает
  РОВНО один узел дерева на один уровень вглубь (может предложить детей, но
  не имеет права сам их запускать), пишет результат строго в формате
  `templates/node.md`.
- **Интегратор** (ты же, другой режим работы, не отдельный агент) —
  применяет ПРЯМЫЕ, нетривиальные-но-однозначные следствия уже принятого
  факта к соседним resolved-узлам, без полного цикла
  stale→субагент→AskUserQuestion. Используется командой `/plan-integrate`
  (см. ниже). Его смысл — не нагружать пользователя подтверждением решений,
  у которых объективно нет развилки (например "раз аккаунт может быть и
  покупателем, и поставщиком — значит профиль обоих роляей живёт на одной
  сущности", это инженерный факт, не выбор). Интегратор НИКОГДА не решает
  то, что было бы `ambiguous` — если у применения следствия есть
  взаимоисключающий выбор, это немедленно эскалируется пользователю как
  обычно, не "тихо" через интегратора. Граница описана в `/plan-integrate`.
- **Пользователь** — даёт исходную идею и выносит финальный вердикт по любому
  узлу со `status: ambiguous`.

## Формат узла

Каждый узел — папка `plan/<idea-slug>/<path-of-slugs>/node.md`, по шаблону
`templates/node.md`. Ключевые поля:

- `status`: `draft` → `in_progress` → один из терминальных:
  - `done` — проработано, однозначный вывод, см. `## Summary`.
  - `ambiguous` — есть взаимоисключающие варианты без доминирующего, см.
    `## Options`. Ждёт вердикта пользователя.
  - `resolved` — был ambiguous, пользователь дал вердикт, записан в
    `## Options` (Verdict/Verdict reason) и перенесён в `## Summary`.
  - `needs_split` — субагент считает тему слишком большой для одного вызова,
    предложил список детей в `## Children` (без их содержимого), ждёт твоего
    решения запускать ли их.
  - `stale` — родитель изменился после того, как этот узел был проработан;
    требует повторного запуска субагента на этом узле.
  - `resolved_needs_split` — составной статус: узел был `ambiguous`,
    пользователь дал вердикт (как в `resolved`), но содержание узла
    ПОСЛЕ применения вердикта всё ещё слишком широко для одного Summary —
    родитель одновременно фиксирует решённую развилку и список
    предложенных детей в `## Children`. Обрабатывается как `resolved`
    (вердикт уже записан, не ждёт пользователя по самой развилке) + как
    `needs_split` (дети не запущены, ждут твоего решения запускать ли их).
    Не путать с обычным `needs_split`: там решения вообще нет, только
    дробление; здесь решение есть, но после него всё равно нужно дробить.
- `depends_on` — id других узлов (не только предок/потомок), от содержания
  которых зависит этот узел. Используй при обнаружении межкомпонентных
  конфликтов.
- `neighbors` — id узлов на том же уровне дерева (братья/сёстры), которые
  субагент должен знать, чтобы не выдать несовместимое решение.
- `parent_hash` — sha256 содержимого `## Context` + `## Summary` родителя на
  момент, когда этот узел был (пере)проработан. Используется для детекта
  staleness.

ID узла = путь slug-имён от корня, без нумерации (например
`auth/token-storage`). Порядок среди соседей задаётся порядком перечисления
в `## Children` родителя, а не числовым префиксом папки.

## Производные артефакты

Дерево (`plan/<slug>/root/...`) отвечает на вопрос "что мы решили и
почему". Иногда после того как ветка (или всё дерево) разрешена, нужен
другой жанр документа — "как это реализовать технически": схема БД,
контракты между сервисами, инфраструктурные требования, диаграммы и т.п.
Это не узел дерева (не использует формат `templates/node.md`, не имеет
`status`/`Options`/`Children` в том же смысле) — отдельный, параллельный
слой, физически размещаемый в `plan/<slug>/tech/` (рядом с `root/`, не
внутри него), создаётся командой `/plan-synthesize`.

Правила этого слоя:
- **Производный, не источник истины.** При расхождении между `tech/*.md`
  и деревом решений приоритет у дерева — техслой нужно пересобрать, не
  наоборот.
- **Трассируемость обязательна.** Каждое решение в техническом документе
  должно явно ссылаться на узел-источник (например "см.
  root/payments-billing — custody вариант C"), чтобы документ не
  превратился в самостоятельный источник истины, расходящийся с деревом.
- **Новые технические развилки (не архитектурные) — не решаются тихо.**
  Если синтез обнажает выбор ниже уровня архитектурных узлов (конкретная
  СУБД, конкретный вендор, конкретная сеть) — дай рекомендованный дефолт,
  но вынеси явным отдельным блоком "требует подтверждения пользователя",
  не похорони внутри обычного текста.
- **Инвалидация — вручную, не автоматическая.** В отличие от узлов
  дерева, изменение узла НЕ каскадирует stale на технический слой сам по
  себе (слишком дорого пересобирать техдокумент на каждую правку).
  Вместо этого каждый артефакт хранит `derived_from_hashes` (см.
  `/plan-synthesize`), и `/plan-status` явно показывает, какие
  tech-артефакты устарели относительно текущих хэшей дерева — решение
  пересобирать остаётся за пользователем.

## Команды

### /plan-dive <идея>

1. Спроси пользователя короткое название идеи (slug), если не очевидно из
   текста — используй его для `plan/<slug>/`.
2. Создай `plan/<slug>/_meta.json` по шаблону.
3. Создай корневой узел `plan/<slug>/root/node.md`: `## Context` = сама идея
   как её дал пользователь, `status: draft`.
4. Запусти **одного** субагента (Agent tool, свежий агент, не fork — субагент
   не должен иметь твой диалоговый контекст, только то, что ты явно передашь)
   на корневой узел с промптом по шаблону "Промпт субагента" ниже.
5. Обработай результат (см. "Обработка результата узла").
6. Если корень вернулся с детьми (`## Children` заполнен) — для КАЖДОГО
   ребёнка создай его `node.md` (status: draft, Context = релевантный срез
   от родителя + упоминание neighbors), и запусти по одному субагенту на
   каждого ребёнка **параллельно** (несколько Agent-вызовов в одном
   сообщении).
7. Собери результаты, покажи пользователю сводку дерева (`/plan-status`
   формат) и список новых ambiguous/needs_split узлов, если есть — задай
   вопросы через AskUserQuestion.

Глубже одного уровня за раз НЕ уходи сама по себе — следующий уровень
прорабатывается следующим вызовом `/plan-dive` (или твоим собственным
продолжением в рамках той же сессии), по явному или подразумеваемому OK
пользователя продолжать вглубь.

### /plan-resume [<idea-slug>]

1. Если slug не дан и в текущей папке один `plan/*/`, возьми его; если
   несколько — спроси.
2. Рекурсивно прочитай дерево узлов (все `node.md`).
3. Построй и покажи пользователю сводку: дерево с status на каждом узле,
   отдельно выведи все `ambiguous` и `needs_split`.
4. Если есть `ambiguous` — задай пользователю вопросы через AskUserQuestion
   (один вопрос на узел, options из `## Options` таблицы + "ещё подумать"
   не предлагай — пусть явно попросит), и запиши вердикты (см.
   "Запись вердикта"). Реальный ответ пользователя часто НЕ совпадает
   буквально ни с одним предложенным вариантом (уточнение/гибрид/свой
   синтез) — это ожидаемо, не исключение; записывай его как отдельный
   Option (например "D"/"custom") с полной формулировкой пользователя,
   не пытайся силой подогнать его под A/B/C.
5. Если есть `needs_split`, спроси пользователя, запускать ли предложенных
   детей сейчас.
6. Для всех `draft`/`stale` узлов — предложи продолжить проработку
   (запустить субагентов), не делай это автоматически без подтверждения,
   если их много (>3) — это может быть дорого.

### /plan-resolve <node-id> <вердикт>

Используется, когда пользователь уже знает, какой вариант выбрать, без
отдельного прохода через AskUserQuestion (например вставляет вердикт прямо в
команду).

1. Открой `node.md` этого узла, убедись `status: ambiguous`.
2. Запиши вердикт в `## Options` (`Verdict:`, `Verdict reason:` — спроси
   причину, если пользователь не дал, коротко почему).
3. Перепиши `## Summary` в соответствии с выбранным вариантом.
4. `status: resolved`, обнови `updated`.
5. Пересчитай хэш этого узла и сравни с `parent_hash` у его детей (если
   есть) — если расходится, пометь их `stale` и сообщи пользователю, что
   поддерево требует повторной проработки.

### /plan-rework <node-id> [новый контекст/правка]

Используется, когда верхний узел меняется и нужно пересчитать затронутых
потомков.

1. Применяется правка к `node.md` указанного узла (Context/Summary).
2. Пересчитай sha256 содержимого узла.
3. Для каждого прямого ребёнка: сравни новый хэш с его `parent_hash`.
   - Совпадает (узел не трогали, он просто не видит изменений) — не трогаем.
   - Не совпадает — пометь ребёнка `stale`.
4. Покажи пользователю список узлов, стaвших `stale`, спроси подтверждение
   на перезапуск субагентов по ним (не делай это сама без подтверждения).
5. ВАЖНО: инвалидация НЕ каскадируется автоматически на внуков. Каждый
   stale-узел при повторной проработке сам решит (новый вызов субагента),
   изменилось ли что-то существенное для его собственных детей, и если да —
   пометит их stale в свою очередь на следующем шаге. Это чтобы не
   пересчитывать всё дерево за одну правку корня.

### /plan-deepen <node-id>

Используется, когда узел уже `resolved`/`done`, но факты, появившиеся
ПОСЛЕ его проработки у соседей (не у его собственных предков — для этого
есть `/plan-rework`), меняют расклад настолько, что исходное решение
стоит пересмотреть заново, более глубоко. Отличие от `/plan-rework`:
rework правит контент конкретного узла и каскадирует вниз по его детям;
deepen запускает повторный, более глубокий проход субагента НАД уже
решённым узлом, без изменения его собственного текста до этого момента —
типичный кейс: "мы решили X при недостатке информации, теперь соседние
узлы резолвились и решение X перестало быть однозначным/симметричным".

1. Собери актуальный срез соседей/зависимостей (как для обычного
   субагента), явно включая то, что изменилось с момента, когда этот узел
   был впервые проработан.
2. Запусти свежего субагента с промптом по тому же шаблону, но явно
   отметь: "это повторная, более глубокая проработка уже решённого узла —
   вот что изменилось у соседей с прошлого раза: <список>. Проверь, не
   стал ли первоначальный вывод неоднозначным или устаревшим".
3. Обработай результат как обычно (см. "Обработка результата узла") —
   если субагент приходит с новым выводом (включая новый `ambiguous`,
   если то, что раньше казалось очевидным, перестало быть таковым) —
   это нормальный исход, не ошибка.
4. Если узел имел детей — сравни новый хэш со старым `parent_hash`,
   расхождение → `stale`, как при любой другой правке узла.

### /plan-integrate <node-id> <новый факт> <затронутые узлы>

Используется интегратором (см. "Роли") для применения тривиального,
однозначного инженерного следствия уже установленного факта к другим
resolved-узлам — БЕЗ полного цикла stale→субагент→AskUserQuestion. Это
не замена `/plan-rework`, а более лёгкий путь для случаев, где развилки
объективно нет.

**Критерий применимости (оба обязательны):**
- Следствие не требует выбора между взаимоисключающими путями — есть
  ровно один разумный инженерный ответ (если ты видишь больше одного
  разумного ответа — это не задача для `/plan-integrate`, эскалируй
  пользователю как обычно).
- Следствие локальное — затрагивает конкретные, явно перечислимые узлы
  точечной правкой (новое поле, новая секция "Х — следствие Y"), не
  требует пересмотра их Summary/Options целиком.

Если сомневаешься, подходит ли случай — не используй `/plan-integrate`,
используй обычный путь (stale + субагент или прямой вопрос пользователю).
Ошибка в сторону лишнего вопроса пользователю дешевле, чем тихо решённая
развилка.

1. Для каждого затронутого узла — примени следствие напрямую (Edit
   `node.md`): добавь секцию с понятным заголовком (например
   "## <Тема> — <суть следствия> (решено интегратором)"), опиши факт и
   его прямое следствие, сошлись на узел-источник факта.
2. НЕ меняй `status` на `stale`/`ambiguous` только из-за этой правки —
   если применённое следствие действительно тривиально, узел остаётся
   в своём текущем статусе (resolved/done). Если применение факта
   обнажило настоящую развилку, которую раньше не было видно — остановись,
   это больше не `/plan-integrate`, эскалируй пользователю.
3. Пересчитай хэш узла, если у него есть дети (как при любой правке).
4. Сообщи пользователю одной строкой, что было сделано и почему это не
   требовало отдельного вопроса (например: "buyer=supplier → обновил
   payments-billing/supply-model/kyb-export на объединённую модель
   данных, т.к. альтернативы не было").

### /plan-synthesize <idea-slug> [<area>]

Используется, когда дерево (или его часть) достаточно разрешено
(`done`/`resolved`), и нужно собрать из него производный технический
артефакт — например схему БД, межсервисные контракты, инфраструктурные
требования, диаграмму. Это НЕ узел дерева (не создавай `node.md` для
результата) — отдельный слой, см. "Производные артефакты" ниже.

1. Убедись, что узлы, релевантные запрошенной области (`<area>`, если
   указана — иначе всё дерево), не в статусе `ambiguous`/`needs_split`/
   `stale`. Если есть — предупреди пользователя, что синтез будет
   частичным/может потребовать пересборки позже, и спроси, продолжать ли.
2. Запусти синтез (обычно через fork, т.к. это чтение многих узлов без
   нужды держать их в основном контексте координатора) с инструкцией:
   перевести факты узлов в конкретный технический формат, явно ссылаясь
   на узел-источник для каждого решения, не изобретая новых архитектурных
   развилок (если встречается настоящая новая развилка технического
   уровня — помечать отдельно как "требует подтверждения пользователя",
   не решать тихо).
3. Запиши результат в `plan/<slug>/tech/<area-or-default-name>.md`.
4. В начале каждого созданного файла зафиксируй `derived_from_hashes` —
   список `{node_id, hash}` для каждого узла, факты которого вошли в
   синтез (тот же sha256-механизм, что `parent_hash` у узлов). Это даёт
   `/plan-status` возможность определить, что технический слой устарел.

### /plan-status [<idea-slug>]

Только чтение — распечатай дерево как есть, с статусами, без запуска
субагентов и без вопросов. Формат:

```
root [done]
├─ auth [done]
│  ├─ token-storage [ambiguous] ← needs verdict
│  └─ session-refresh [done]
└─ billing [needs_split] ← predicted children: invoicing, metering

tech/
└─ db-schema.md ← stale (root/auth changed since synthesis)
```

Если в `plan/<slug>/tech/` есть артефакты — для каждого сравни
`derived_from_hashes` с текущими хэшами соответствующих узлов; расхождение
→ выведи артефакт как `stale` в сводке (не пересобирай сам, просто
предупреди — пересборка через `/plan-synthesize` по явному запросу).

## Промпт субагента (шаблон)

При запуске субагента на узел передавай ЕМУ, и только ему релевантное:

```
Ты прорабатываешь ОДИН узел дерева архитектурного плана. Не уходи глубже
одного уровня — если тема требует дальнейшего дробления, предложи детей, но
не прорабатывай их содержимое сам.

## Текущий узел
id: <id>
<содержимое ## Context текущего узла>
```

## Обработка результата узла

Когда субагент вернул результат:

1. Распарси frontmatter + секции.
2. Проверь, что status один из `done|ambiguous|needs_split` — если нет,
   переспроси субагента (это ошибка формата, не повод эскалировать
   пользователю).
3. Посчитай sha256 от (Context + Summary) этого узла — это `parent_hash`,
   который пойдёт в детей, если их создашь.
4. Запиши `node.md`.
5. Если `status: ambiguous` — не блокируй остальное дерево, продолжай
   обработку других узлов, собери все ambiguous в конце прохода и задай
   пользователю вопросы одним батчем (несколько вопросов в одном вызове
   AskUserQuestion, если их несколько).

## Запись вердикта

Когда пользователь дал вердикт по ambiguous-узлу (через AskUserQuestion
или напрямую в сообщении):

1. `## Options`: добавь `Verdict: <выбранный вариант>` и
   `Verdict reason: <почему, из ответа пользователя, если дал — иначе
   "пользователь не пояснил">`. Если ответ не совпадает буквально ни с
   одним предложенным вариантом — не подгоняй его под существующий, добавь
   как новый вариант (следующая буква/`custom`) с полным текстом
   пользователя как содержанием, и ссылайся на него в Verdict. Это
   нормальный, частый случай, не отклонение от протокола.
2. `## Summary`: перепиши под выбранный вариант.
3. `status: resolved` (или `resolved_needs_split`, если после применения
   вердикта тема всё равно требует дробления на детей — см. "Формат узла").
4. Если у узла есть дети — сравни новый хэш со старым `parent_hash` у
   каждого; расхождение → `stale`, сообщи пользователю.
5. Если вердикт устанавливает новый факт, который явно противоречит или
   дополняет контекст, принятый в УЖЕ resolved/done соседних узлах (не
   только детях) — не оставляй это молча. Либо пометь затронутые
   соседние узлы `stale` и предложи пользователю полный пересчёт через
   `/plan-rework`, либо, если последствие тривиальное и однозначное (нет
   развилки, только инженерное домножение факта — см. критерий в
   `/plan-integrate`), примени его через `/plan-integrate` вместо того,
   чтобы оставлять несогласованность в дереве.

## Важные принципы

- **Не углубляйся без спроса.** Каждый `/plan-dive` или продолжение дерева
  вглубь — это заметные траты (параллельные субагенты). Один уровень за раз,
  дальше — явное "продолжай" от пользователя.
- **Финальный вердикт по ambiguous — только пользователь.** Субагент и ты
  сам никогда не выбираете за него взаимоисключающий путь. Рекомендация —
  да, выбор — нет.
- **Context у субагента — сжатый, не полное дерево.** Передавай только
  Context/Summary соседей и зависимостей, не сырые node.md целиком и не
  историю диалога с пользователем.
- **Инвалидация построчная, не каскадная за один проход.** Правка узла
  помечает stale только прямых детей; дальше — по мере их собственной
  повторной проработки.
- **Всё на диске.** Ничего важного не держи только в своём контексте диалога
  — если сессия прервётся, `/plan-resume` должен восстановить полную картину
  из файлов.
- **Кастомные/гибридные вердикты — норма, не отклонение.** Пользователь
  часто отвечает не буквально одним из предложенных вариантов, а
  уточнением или синтезом нескольких. Записывай это как отдельный
  вариант с полным текстом пользователя, не форси выбор под A/B/C.
- **Интегратор — только для бесспорных следствий.** `/plan-integrate`
  существует, чтобы не гонять пользователя через AskUserQuestion по
  вещам, у которых объективно нет развилки (прямое инженерное
  распространение уже принятого факта). Как только появляется реальный
  выбор — это немедленно возвращается на обычный путь эскалации, никогда
  не решается "по умолчанию" интегратором или координатором.
- **Производные артефакты трассируемы и ревалидируемы, не вечны.**
  `tech/`-слой — это снимок на момент синтеза, не живая часть дерева;
  `/plan-status` должен уметь сказать, что он устарел, не притворяться,
  что он автоматически в курсе изменений дерева.
